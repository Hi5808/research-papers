# Cross-Vendor Edge Inference: Jetson Orin NX (TensorRT-Edge-LLM) vs. RK3588 (rkllama/NPU) on the Same Model Family

**Platform A:** Seeed Studio reComputer J4012 — NVIDIA Jetson Orin NX 16GB (module P3767-300), JetPack 7.2, CUDA 13.2
**Platform B:** Rock 5B+ — Rockchip RK3588 (NPU + Mali-G610 GPU + Cortex-A76/A55 CPU), 8GB RAM
**Date:** August 2026 (Orin figures reused from the companion tokens-per-joule paper's 2026-08-11 campaign; RK3588 figures from an independent, longer-running NPU characterization effort on the same host, same window)

## Abstract

This project has independently benchmarked Qwen3-1.7B and Qwen3-4B on two different edge accelerator architectures — Jetson Orin NX's CUDA-based TensorRT-Edge-LLM stack, and the RK3588's NPU via `rkllama`/`rknn-llm` — without originally intending a head-to-head comparison. Bringing the two datasets together here for the first time: at their respective best-measured configurations, Orin NX's decode throughput for Qwen3-1.7B is **~4x** the RK3588 NPU's, and its energy-per-token is markedly lower. For Qwen3-4B, no clean RK3588 decode number exists at all — the RK3588's 8GB of RAM proved insufficient to complete a 16k-context decode benchmark for a 4B model, a genuine negative result documented here rather than a missing data point glossed over. The comparison carries a real, stated confound: the two stacks use different quantization schemes (NVFP4-family weight-only on Orin vs. INT8 activation+weight, `w8a8`, on RK3588), following the same honest-caveat pattern as this project's existing TensorRT-Edge-LLM-vs-llama.cpp paper. The RK3588 numbers used here already represent the *best* configuration found after an extensive independent investigation (DDR/CPU-governor/GPU-driver fixes, `w8a8_g128`-vs-plain-`w8a8` quantization comparison) that closed a 3.2x gap against Rockchip's own published figures down to 1.7x — these are not naive out-of-the-box numbers being unfairly compared against a tuned Orin.

## 1. Qwen3-1.7B: Decode Throughput and Efficiency, Head to Head

| Platform | Decode tok/s | Power draw | Energy/token |
|---|---|---|---|
| Orin NX, TensorRT-Edge-LLM, 40W mode (Pareto-optimal, from companion paper) | **58.1** | 17.890 W | **0.308 J/token** |
| RK3588 NPU, `rkllama`, best-tuned config (plain `w8a8`, post DDR+governor+GPU fixes) | **14.55 ± 0.31** | not independently logged in the source investigation at this specific configuration | — |

Orin's 40W figure is reused directly from the companion tokens-per-joule paper (§3.2 of that paper), itself already the Pareto-optimal point across five `nvpmodel` modes measured there. The RK3588 figure is the best decode throughput reached across an extensive independent tuning investigation on that board (see `~/npu-bench/REPORT.md` on the Rock 5B+ host) — starting from a 6.45 tok/s naive baseline, and stacking DDR timing fixes, CPU governor changes, a GPU/OpenCL driver overlay swap (`panthor`→`midgard`), and a switch from grouped (`w8a8_g128`) to plain `w8a8` quantization to reach 14.55 tok/s. That investigation independently confirmed (via `airockchip/rknn-llm` issue #409, a different user on different RK3588 hardware and a different model) that this ~1.7-3x shortfall against Rockchip's own published benchmark figures is not specific to this unit — a real, reproducible tooling/documentation gap on the vendor's side, not a one-off misconfiguration this project introduced.

**Orin NX wins by roughly 4x on decode throughput for the same model family**, even against the RK3588's best-tuned, gap-closed configuration rather than an out-of-the-box number. This is a meaningfully larger margin than the 28-65% TensorRT-Edge-LLM-vs-llama.cpp gap documented on Orin alone in the companion paper — the architecture difference (dedicated CUDA cores + mature toolchain vs. a real NPU with an immature, C++-demo-first toolchain that itself needed a 3.2x-to-1.7x tuning campaign to become competitive) dominates any within-platform software-stack choice.

## 2. Qwen3-4B: A Negative Result, Not a Missing Data Point

Orin NX's Qwen3-4B decode figure at 40W (companion paper): **30.1 tok/s at 20.074 W → 0.667 J/token.**

No equivalent RK3588 decode figure exists. The independent RK3588 investigation attempted a 16k-context long-context sweep for `Qwen3-4B-rk3588-1.2.1-unsloth-16k` and got exactly one clean data point — 1024-token prefill at 25.9 tok/s — before RAM exhaustion aborted the run. Loading this model with `NUM_CTX=16384` pre-allocates KV cache sized for the *full* 16k window immediately at load time, regardless of actual prompt length tested: RSS reached ~6.1GB on load alone on an 8GB board, and a subsequent trial's available memory dropped to 121MB, triggering the harness's 800MB safety-floor abort before an actual OOM crash. Unloading the model fully recovered the 6GB, confirming this is a load-time allocation choice in the `rkllm` runtime, not a memory leak.

**This is reported as a finding, not a gap in this paper's methodology**: on an 8GB RK3588 board, a 4B-class model with genuinely large (16k) context support is RAM-constrained before it is compute-constrained, at the point of model *load*, independent of how much of that context window a given request actually uses. A fair decode-throughput comparison at this model size and context length is not achievable on this specific board configuration without either a smaller model, a lower context limit set at conversion time (trading away the capability being tested), or more system RAM than this unit has.

## 3. The Precision Confound, Stated Plainly

Following this project's own established practice (see the companion TensorRT-Edge-LLM-vs-llama.cpp paper's §4): Orin's engines use NVIDIA's NVFP4-family weight-only quantization; RK3588's use `w8a8`, an INT8 activation+weight scheme. These are not the same precision class, and some portion of the throughput gap in §1 plausibly reflects this rather than pure architecture/toolchain maturity. Unlike the llama.cpp comparison, this project has not attempted to find or produce a matched-precision pair across these two specific stacks — RK3588's `rkllm` toolchain and TensorRT-Edge-LLM do not share a common quantization format, and neither converts the other's checkpoints directly (a similar tensor-layout mismatch to the one documented in the llama.cpp paper). Closing this confound would require quantizing the same source checkpoint independently to a matched scheme on each toolchain (e.g., both to their closest available INT8 variant) — not attempted here, left as a possible follow-up if a genuinely apples-to-apples number is wanted over the current best-effort comparison.

## 4. Conclusion

For Qwen3-1.7B, Orin NX's CUDA-based stack outperforms the RK3588 NPU's best-tuned configuration by roughly 4x on decode throughput and by a comparable margin on energy-per-token — a real, substantial gap that holds even after accounting for the RK3588 side representing extensive independent tuning work (documented via real upstream issue-filing, not a naive baseline) rather than an unfair out-of-the-box comparison. For Qwen3-4B, no comparison is possible at all on this specific RK3588 unit at the context length tested — RAM exhaustion at model load time is itself the finding, and is reported as such rather than papered over with a smaller, less representative test. The stated precision confound (NVFP4-family vs. `w8a8`) means this paper's throughput gap should be read as "these two real, currently-available toolchains, as commonly used" rather than "this SoC architecture is inherently 4x faster" — disentangling architecture from quantization scheme is left as explicit future work.
