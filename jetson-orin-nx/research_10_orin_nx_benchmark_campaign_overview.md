# Four Benchmark Campaigns on Jetson Orin NX 16GB: What Nobody Had Published Yet

**Platform:** Seeed Studio reComputer J4012 — NVIDIA Jetson Orin NX 16GB (module P3767-300) on a J401 carrier board
**Software stack:** JetPack 7.2, L4T R39.2.0, CUDA 13.2, TensorRT 10.16.2.10, TensorRT-Edge-LLM, llama.cpp
**Date:** August 2026

## Abstract

This paper indexes and synthesizes four companion papers, all run on the same physical Orin NX unit already characterized in this project's strip/tune and power-ceiling work, chosen specifically to fill gaps a quick literature check confirmed were genuinely open: a published Orin Nano tokens-per-joule curve exists with no Orin NX equivalent; nobody had correlated this SoC's hardware over-current protection with actual LLM inference behavior; TensorRT-Edge-LLM vs. llama.cpp comparisons on Jetson rarely control for model and hardware simultaneously; and DLA+GPU concurrent utilization during LLM inference is essentially unexplored in public benchmarking. Three of the four campaigns produced substantive, evidence-backed findings; the fourth (DLA) produced a clean negative result — the hardware initializes but the software stack cannot use it — which is itself a documented gap worth knowing about before planning around it. Two operational lessons recur across all four campaigns and are collected here rather than repeated: `nvpmodel` mode switches into 10W/15W require an interactive reboot confirmation that silently fails over a non-interactive SSH session, and this board intermittently loses its GPU `devfreq` governor node across reboots for reasons not fully root-caused.

## 1. What Each Campaign Found

**Tokens-per-joule across all five `nvpmodel` power modes** ([research_11](research_11_orin_nx_tokens_per_joule.md)): the Orin Nano's published efficiency-optimal mode (25W) does not transfer. On this Orin NX, efficiency *degrades* from 10W through 25W and only improves at 40W — the actual Pareto-optimal mode on this hardware — because the per-mode GPU clock/TPC table is non-monotonic (25W runs 4 TPCs at a *lower* clock than 10W/15W's 2 TPCs; full GPU throughput only unlocks at 40W). A deployment picking a power mode by wattage label alone, or by extrapolating Nano guidance to NX hardware, would very likely choose an inferior mode.

**Correlating hardware over-current throttling with LLM inference** ([research_12](research_12_orin_nx_oc_throttle_latency.md)): the `soctherm_oc` protection this project's power-ceiling paper found firing hundreds of times per second under synthetic stress does not engage during single-stream decode inference at all — decode is too light a GPU workload to trigger it, with or without concurrent CPU load. It does engage during prefill under concurrent CPU load (13,726 events in ~27 seconds triggered a measured 10.1% throughput drop), but the effect is a sustained higher latency floor, not increased jitter — per-iteration timing variance actually *decreased* under throttling. Decode-dominated serving workloads can disregard this entirely; prefill-heavy workloads under concurrent host load cannot.

**TensorRT-Edge-LLM vs. llama.cpp, matched model and hardware** ([research_13](research_13_orin_nx_trtllm_vs_llamacpp.md)): TensorRT-Edge-LLM wins decisively — 57-65% faster prefill, 28-50% faster decode, depending on model size — and since both stacks draw nearly identical power on this hardware, the efficiency gap tracks the throughput gap almost exactly. This isn't a speed-for-power tradeoff. The comparison carries a real, disclosed confound (the two stacks use different quantization schemes, since llama.cpp cannot ingest NVIDIA's NVFP4-family quantized checkpoint format directly), but the gap is large enough that it should dominate a deployment decision on this hardware regardless.

**Concurrent DLA+GPU utilization** ([research_14](research_14_orin_nx_dla_unavailable.md)): could not be run. DLA hardware initializes cleanly at the kernel level — both cores present, clocked, no driver errors — but TensorRT reports zero available DLA cores on this JetPack 7.2 / TensorRT 10.16.2.10 build, and no DLA compiler package exists anywhere in this release's apt repository to fix it. This is a negative result worth publishing precisely because most Jetson content assumes DLA "just works" once the cores are present; here, demonstrably, it doesn't.

## 2. Two Reliability Traps That Cut Across All Four Campaigns

**`nvpmodel -m` into 10W or 15W silently fails without an interactive reboot confirmation.** This is a sharper, more specific version of an issue already flagged in this project's companion fan-curve paper (`nvpmodel -m` can report success and silently revert). The actual mechanism, isolated during campaign 11's sweep: `nvpmodel -m 1` (10W) prompts `DO YOU WANT TO REBOOT NOW? enter YES/yes to confirm:` when the target mode requires a reboot, and a non-interactive SSH invocation has no TTY to answer it — the command fails with `NVPM ERROR: bad input!`, the mode never changes, and nothing about the exit status distinguishes this from success. The fix is to pipe an explicit confirmation (`printf '<password>\nyes\n' | sudo -S nvpmodel -m <id>`) and then wait out an actual reboot, re-verifying `nvpmodel -q` afterward rather than trusting the command that set it. Not every mode transition requires this — 15W→25W and 25W→MAXN_SUPER applied immediately in this session's testing — so it isn't a fixed cost per switch, but it must be checked for, not assumed.

**The GPU `devfreq` governor node intermittently goes missing after a reboot.** On roughly two of five boots during this session's testing, `/sys/class/devfreq/17000000.gpu` was absent immediately after boot, causing `nvpmodel.service` to fail and `jetson_clocks --show` to report `Error! GPU frequency scaling not supported!` — while the GPU itself continued to function normally for actual compute. This cleared on a subsequent reboot each time it occurred. The underlying cause (a driver-load race specific to this board's software configuration) was not root-caused further in this session, but it means clock-locked benchmarking on this board requires checking for the presence of this devfreq node before trusting `jetson_clocks` output, not just checking the command's exit code.

Both of these compounded during campaign 11's power-mode sweep in a way worth flagging for anyone reproducing similar work: a background build process (llama.cpp's, in campaign 13) does not survive a `nvpmodel`-triggered reboot even when launched with `nohup`/`disown`, since a full system reboot kills everything regardless. Sequencing matters — finish reboot-requiring power-mode work before starting a long unattended build, not concurrently.

## 3. Conclusion

Three genuinely new, evidence-backed findings and one clean negative result came out of deliberately targeting gaps a literature check confirmed were open, rather than re-measuring throughput numbers that already exist elsewhere. The throughline across all three positive findings is the same: guidance that holds for one Jetson SKU (the Orin Nano's efficiency-optimal power mode, general assumptions about DLA availability, throttling behavior inferred from synthetic stress tests) does not reliably transfer to a different SKU, a different software stack, or a different workload phase, and has to be re-measured directly rather than assumed. The reliability traps in §2 are offered as a practical contribution in their own right — both cost real time in this session and would cost more for anyone reproducing this work without knowing to check for them upfront.
