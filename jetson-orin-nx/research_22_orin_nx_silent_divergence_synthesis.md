# The Silent Divergence Pattern: What Thirteen Papers of Direct Measurement on One Jetson Orin NX Actually Add Up To

**Platform:** Seeed Studio reComputer J4012 — NVIDIA Jetson Orin NX 16GB (module P3767-300) on a J401 carrier board
**Software stack:** JetPack 7.2, L4T R39.2.0, CUDA 13.2
**Scope:** synthesis of papers 9, 11-15, 19, 21 (this board) plus 16-18, 20 (adjacent hardware, cited for contrast) — August 2026
**Date:** August 2026

## Abstract

This project has now run thirteen independent, direct-measurement investigations on a single Jetson Orin NX unit: desktop stripping and performance tuning, power-mode efficiency across all five `nvpmodel` states, over-current throttling under different workload shapes, TensorRT-Edge-LLM vs. llama.cpp, DLA availability, TensorRT-Edge-LLM version compatibility, Ollama's JetPack 7.2 GPU detection, and CUDA MPS concurrency. Read individually, these are unrelated bug reports and benchmark results. Read together, they converge on a single, load-bearing pattern this paper names explicitly: **on this board's software stack, almost nothing fails loudly.** The GPU never fails to hit 40W with an error — it silently throttles under `soctherm_oc` while `nvpmodel` and every user-facing tool keeps reporting MAXN_SUPER as active and normal. Applying the previous Orin Nano generation's published power-mode guidance doesn't error — it just silently produces worse throughput and efficiency, because this board's mid-tier power modes trade GPU clock for TPC count in a way the Nano's don't. The DLA cores initialize cleanly in `dmesg` and `jetson_clocks --show` — TensorRT just silently reports zero available cores, with no compiler package anywhere to fix it. Ollama's official installer prints an alarming failure warning that is, in this case, itself the false signal — the underlying binary works fine regardless. A stale TensorRT-Edge-LLM engine doesn't refuse to load with a clear "wrong version" error — it fails two log lines later with an opaque plugin-registry error. CUDA MPS starts, accepts clients, and runs without complaint while doing nothing measurable. In every one of these cases, the tool's own surface-level status output — a running service, a clean log, a mode name, a successful build, a version number — was not sufficient evidence that the thing it claimed to be doing was actually happening as expected. The practical conclusion this synthesis draws is not "this board is bad" (it consistently performs well once its real behavior is understood) but that **direct, register-level or output-level measurement is not optional supporting evidence on this hardware/software stack — it is the only reliable signal**, and any deployment or benchmarking practice that trusts a tool's own reported status without an independent check is likely already wrong somewhere and doesn't know it.

## 1. The Pattern, Instance by Instance

| Subsystem | What the surface signal says | What direct measurement found | Paper |
|---|---|---|---|
| Power mode / thermal ceiling | `nvpmodel -q` reports MAXN_SUPER active, no error | Board never actually draws the 40W nameplate implies; `soctherm_oc` fires ~200x/sec under load, silently capping real power at ~34-40W depending on workload | 9, 12 |
| Power-mode efficiency | Nano's published guidance says a mid-tier mode (25W-class) is most efficient | On this board, efficiency *degrades* monotonically from 10W→25W (non-monotonic GPU clock/TPC table) and only improves at 40W — following the Nano's guidance would silently pick a worse mode with no error telling you so | 11 |
| DLA cores | `dmesg` and `jetson_clocks --show` report both DLA cores online, clocked, functioning | TensorRT silently reports zero available DLA cores; no compiler package exists anywhere in the JetPack 7.2 apt repository to fix it | 14 |
| TensorRT-Edge-LLM engine compatibility | An older engine file loads without a hard block | A one-line, easy-to-miss version-mismatch *warning* is followed two log lines later by an opaque `IPluginRegistry` deserialization failure that gives no indication the real cause is version skew | 15 |
| TensorRT-Edge-LLM v0.10.0 build | `cmake`/`make` follow the officially documented platform command exactly | Compilation fails outright on Orin — a real, filed upstream bug (NVIDIA/TensorRT-Edge-LLM#178) where the shipped CuTe DSL kernel artifact for this platform is simply incomplete, silently missing kernel modules the newly-migrated FMHA backend requires | 15 |
| Ollama GPU detection | Install script prints "Unsupported JetPack version detected, GPU may not be supported" | The warning itself is the misleading signal here — the underlying binary's own CUDA runtime selection (`cuda_v12`→`cuda_v13` fallback) works correctly regardless, confirmed via real `tegrastats` GPU utilization | 19 |
| CUDA MPS | Control daemon starts cleanly, accepts client connections, no errors logged | Provides no measurable throughput benefit for the tested workload at either 3 or 6 concurrent processes — and a naive first-run comparison would have reported the *opposite*, wrong conclusion due to an unrelated cold-start artifact | 21 |

Seven subsystems, seven cases where the artifact a user or an automated pipeline would normally trust — a status query, a log line, a successful build, an install script's own warning — was not a reliable predictor of the actual underlying behavior. Three of the seven (DLA, TensorRT-Edge-LLM v0.10.0, MPS) fail in the direction of *silently doing less than claimed*; one (Ollama) fails in the direction of *silently claiming to do less than it actually does*; the throttling and power-mode cases fail by *silently substituting a different real behavior for the nominal one while reporting the nominal state as active*. The direction varies. The absence of a clear, immediate, correctly-attributed error signal does not.

## 2. Why This Happens Here Specifically, Not as a Generic Complaint About Software

It would be easy to read this as "software has bugs, more news at 11" — that is not the claim. The specific, load-bearing reason this pattern recurs on *this* hardware/software stack is structural, not incidental: Jetson's SoC-integrated architecture means the GPU, DLA, memory controller, and thermal management are all governed by closed-firmware components (`nvidia,bpmp`, per paper 9's device-tree investigation) that sit *below* the layer any of these tools — `nvpmodel`, `jetson_clocks`, TensorRT, `dmesg`, Ollama's installer — actually query. A discrete GPU on a desktop or server reports its own real state fairly directly; an SoC's firmware-mediated power/clock/compute-availability state can silently diverge from what device-tree-derived driver-level tools report, because those tools are reporting what the driver *believes* the hardware supports, not what the closed firmware is actually doing moment to moment. Papers 9 and 12's root-causing of the throttle behavior specifically required reading `hwmon` register counters directly — not `nvpmodel`, not `tegrastats` at default settings, not any documented, officially-surfaced API — because the actual limiting mechanism operates one layer below where any standard tool looks. The DLA case is structurally identical: kernel driver state (real, verifiable) and TensorRT's userspace capability query (which depends on a separate, absent compiler component) are two different claims that happen to usually agree on properly-provisioned systems and simply don't here.

## 3. What This Changes About How to Approach Future Work on This Board

This synthesis is the actionable output of thirteen papers' worth of accumulated experience, and it changes methodology going forward, not just adds to a list of findings:

- **Never trust a single status signal as sufficient evidence a subsystem is working as intended** — this project's own spec-decode campaign scoping (blocked on NVIDIA/TensorRT-Edge-LLM#178) exists specifically because a documented, officially-recommended build command silently produced a broken toolchain; the pattern this paper describes is not hypothetical, it is why the flagship ongoing campaign is currently stalled.
- **A clean build or a clean log is necessary but never sufficient** — three of the four TensorRT-Edge-LLM-related findings in this project (paper 15's plugin-ABI mismatch, paper 15's missing FMHA artifact, and this synthesis's own DLA/MPS entries) all passed their respective build/start steps without any reported error.
- **When a public guide or a prior-generation board's documented behavior is available, treat it as a hypothesis to verify, not a default to inherit** — paper 11's power-mode finding exists specifically because the Orin Nano's published efficiency curve does not transfer, and nothing about `nvpmodel`'s interface signals that a given mode name means something structurally different on this SKU.
- **The actual ground truth, when it's obtainable at all, lives one layer below the tool you'd normally check** — `hwmon` registers instead of `tegrastats`, `dmesg` cross-checked against TensorRT's own capability query instead of either alone, `tegrastats` GPU utilization instead of an install script's own warning text, raw wall-clock timing instead of a service's "started successfully" log line.

## 4. Conclusion

No single one of this project's thirteen Orin NX papers claims this pattern on its own — each is a narrow, falsifiable, independently-defensible finding about one specific subsystem. What connects them, visible only once collected and read together, is that the tools this platform gives you to check whether something is working — `nvpmodel -q`, `jetson_clocks --show`, `dmesg`, a build's exit code, a daemon's own log, an installer's own warning — are consistently insufficient on their own to answer that question, in both directions (over-claiming success and over-claiming failure), across power management, compute-accelerator availability, ML framework compatibility, and GPU-sharing mechanisms alike. That is the actual, transferable finding this synthesis contributes beyond the sum of its parts: not a specific bug, but a documented, evidenced case that on Jetson Orin NX's closed-firmware-mediated software stack, direct measurement is not a best practice among several reasonable options — it is the only practice that has produced a correct answer, every single time this project has needed one, across thirteen independent investigations.
